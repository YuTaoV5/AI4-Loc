# Jev × 手机 SoC 软件工程：讲稿与讨论提纲

建议时长 25–35 分钟。口径标签：**官方口径**、**第三方评测**、**案例作者自测**、**本汇报推演**。

## 01 封面

今天不把 Jev 当成能替代代码助手的聊天模型，而把它放进手机 SoC 软件研发流程，讨论它作为概率决策组件能做什么。重点是哪些研发判断可以从规则、模型、工程师之间拆出来，再以可审计方式组合。所有 SoC 用例均为研发工具链方案推演，不是华为内部系统现状，也不是 Jev 已在华为产品验证的结论。

## 02 先在研发工具链试点，别进内核热路径

建议先尝试 nightly CI / VTS 失败分流、跨版本回归归因、性能问题排序。它们通常已有原始记录、测试 ID、软件版本和工程师标签，低风险试错时也能保留原流程。相比之下，IRQ、调度、DVFS 或启动路径要求毫秒级、确定性、离线和故障时可预测；当前 Jev 通过托管 API 提供，不公开本地权重，不能因为“模型快”就放进手机端热路径。低置信时转人工，高风险动作仍由代码策略和授权流程控制。

## 03 Jev 回答判断题，不负责写解释

TypeSafe 把 Jev 定义为 System One 模型：调用方发送 state 与若干类型化问题，服务返回受约束的选择 / 分数 / 是否概率。它没有自由文本生成、自然语言解释或代码生成接口。工程上的优势是应用可直接解析返回值；代价是调用方需要预先定义问题和候选空间。若团队需要解释、补丁或复现步骤，应由既有工具、工程师或另一个生成式模型完成，不能指望 Jev 编写原因分析。

## 04 Choice、Score、Noul

Choice 用于互斥标签，例如故障 owner；它会返回候选概率。Score 对一组有序描述做评估，分数是对各等级位置的概率加权结果，例如等级为 0、1、2，概率为 0、0.57、0.43 时 Score 为 1.43。这个数字是等级轴上的期望位置，不是实际发生比例，也不适合反推精确物理量。Noul 返回 P(yes)，适用于独立布尔判断；官方文档指出 Noul answer 不包含 confidence。复杂判断应该拆成多个清晰问题，由代码组合。

## 05 选择取决于数据、时延和部署边界

基线要选对。字符串 / 状态机能准确处理格式和精确数值，且可离线运行；已有标签数据时，监督 encoder 往往更适合固定分类和高吞吐；通用 LLM 擅长生成解释、总结和开放式推理；Jev 的目标是固定问题空间中的语义决策，尤其可快速启动、并行提问、输出概率。评测时应把“谁更准”“谁更快”“谁更便宜”“谁能离线跑”拆成单独指标。不要只拿 Jev 和一个最贵 LLM 比，再据此宣布技术替代。

## 06 官方倍数是特定工作流的上沿

**官方口径**：发布文给出输入每百万 token 0.042 美元，输出 token 免费；发布文称 API 服务时延在 70–500 ms。官网展示最高约 193.6× 更快、444.6× 更便宜。官方自己解释这些是其 workflow 评测中接近高端的收益，评测团队参与了 workflow 设计，参考分布又来自 GPT-6 Astra 与 Fable 5.1 的平均，仍可能有设计偏差。因此这页刻意把倍数标为高端样例。华为实验室应自己测从调用方到服务端的 p50 / p95、并发、429、区域网络与请求长度，别把服务器上游耗时或营销倍数当作本机端到端承诺。

## 07 置信度适合分流，不等于正确率保证

Choice 和 Score 返回概率分布及 confidence。官方解释 confidence 是将分布集中程度压成一个数，分布平坦时置信较低。它确实可以让系统选择自动处理、复核或退出，但“校准”是在一批预测上的统计性质，并不保证单个样本正确。应按子系统、语言、设备版本和故障类别画 reliability curve，计算 ECE / Brier，并报告 selective risk 与 coverage。阈值要随着误报、漏报、错误 owner 的成本改变；不能照抄官网示例里的 0.5 或 0.9。

## 08 已知弱点决定预处理和降级策略

**官方已知限制**包括字面理解、否定句、数学 / 计数 / 日期比较、间接推理、过长且含无关细节的 state、对抗性文本，以及 instruction 与 criteria 冲突。官方建议把计算留在代码里，先过滤大 state，精确定义问题与边界，把 state 当不可信数据并测试对抗输入。Jev 英语为主要训练语言，CJK 可以输入但不保证相同效果。研发记录中也常含 shell 指令、补丁文本或异常注释，所以模型输入不是安全策略引擎，也不能单独抵御 prompt injection。

## 09 有标签数据时，小型 encoder 可能更合适

**第三方预注册研究**在 Banking77 的 paired n=208 子集上报告 Jev 83.2%、GPT-5.6 Terra 87.5%、用约 10,003 条监督样本训练的 encoder 93.3%。表中的耗时是各测试客户端 / 服务组合，不是抽象模型推理速度；Jev 0.44 秒，Terra 1.51 秒，encoder 0.01 秒中位数。单个英文公开意图任务不能排名所有模型，但它说明我们要比较正确的替代方案：对于重复固定的 SoC 故障标签，投入标注训练一个小 encoder 很可能是更可控、更快、更本地化的终态。Jev 可作为标签冷启动、弱监督工具或复杂样本的第二层。

## 10 二次复核可能把正确答案改错

另一个 GitHub 独立试验报告：TREC 200 条样本中，GPT-6 Astra few-shot 从 194/200 正确变成 Jev review 后 173/200；Jev 修正 3 个错误，同时把 24 个原本正确答案改错。研究作者将其描述为探索性测量，单一数据划分和配置不适合泛化。我们把它作为流程反例：二次复核的目标应该是检测不确定性或明确的错误类型，而不是把“再问一次模型”视为无成本增益。若 Jev 要复核 encoder / LLM，需要留独立测试集并特别统计误改率。

## 11 Jev 适合插在召回与规则之间

**参考案例作者自测**：PaperDance 先在约 25 万篇论文库里做全文和向量召回，再以 Jev 概率判断相关度并重排。作者报告 54 篇标注子集英文查询 AUC 0.995，纯中文查询 0.924；又发现少数关键论文概率只有 0.14–0.25。这不是手机 SoC 评测，也不是独立复现。价值在于展示一种组合架构：检索负责找全候选，模型负责模糊语义排序，代码负责阈值与路由，人审负责边界情况。它也提醒我们：总体 AUC 不能掩盖中文和关键少数类召回。

## 12 把判断点放在研发工具链

AOSP 是公开的通用参照：VTS 测 Kernel 与 HAL 实现；Perfetto 可以把多进程、内核、GPU、频率和日志事件合并到系统 trace。这里用这些名词说明可能的数据面，不暗示华为团队使用 AOSP 的内部实现。若实际流程基于自有 Linux/HarmonyOS 分支、厂商测试框架或内部 trace schema，只要能抽取同类版本与事件信息，仍可以采用相同决策服务模式。重点是把结论放在 CI / 分析工作台，而非替代验证工具。

## 13 用例一：CI / VTS 失败分流

先用测试 harness 对失败去重和抽取字段：test ID、板级 revision、kernel build、HAL / firmware 版本、重试比例、关键 log 片段。规则负责精确识别常见错误；Jev 可从有限故障族中推荐 owner 或 severity。返回结果附上证据片段、原始链接与概率，工程师确认后再回写标签库。模型不得静默关闭问题、修改代码、刷机或改变 release gate。成功标准可以是更快找对 owner，且不增加高严重级别故障的漏分。

## 14 用例二：Perfetto trace 到语义回归类别

Perfetto 提供系统级 trace；CPU scheduling 数据可显示线程在哪个核运行、何时被唤醒、何时被阻塞；频率和 GPU 数据源也可用于定位。第一步用 PerfettoSQL / parser 算唤醒到运行延迟 p95、jank 比例、cluster 频率驻留、GPU busy、温度差等。第二步将这些确定性特征和版本差分组合成短 state，再让 Jev 从 scheduler contention、GPU/driver、thermal/power policy、I/O/lock 等标签中做语义路由。模型不应读取二进制 trace，也不应替代计数和统计。功耗 rail 是否可用依平台和 trace producer 而异。

## 15 Bring-up 归因保留版本上下文

同一行 probe error 可能是不同根因。state 至少带 SoC revision、board、PMIC / memory SKU、kernel branch / config、firmware、HAL 版本、cold/warm boot、温度档、测试 ID 与实验室工位。脚本算首次出现的提交区间、跨版本变化和设备矩阵覆盖；Jev 只判断日志语义是否相似、是否可能属于相同故障族、哪个团队先看。相似度不等于因果关系。要通过重现、二分提交、替换配置或硬件测量来确认 root cause。

## 16 最小请求怎么写

示意请求固定 jev-1.13.0，输入英文结构化字段以贴近英文优先的限制。repeat_rate 由测试系统计数，boot_ms_delta 由脚本计算；模型只负责判断 owner、严重度、是否 cold-boot-only。Choice 的候选描述说明责任边界，并保留 unknown。生产版本还应定义 schema 版本、字段缺失行为、输入截断、结果 JSON 校验、请求 ID 和日志脱敏。注意样例仅是方案草图，不是 API 实测返回。

## 17 本地抽取与策略，托管服务只做语义判断

推荐架构是：设备 / 测试场采集原始 dmesg、logcat、tombstone 和 trace；研发主机本地脱敏、去重、聚合并以固定 schema 形成 state；决策服务返回结构化答案；本地策略层根据经过验证的阈值分流或转人工；人审结果回流为后续标注数据。API 无法访问时应完整保留既有流程。把模型包装在 adapter 后面，便于切换 encoder、规则或别的服务。日志原件留在内网时，外发字段和 retention 都要经过组织数据治理。

## 18 托管服务与手机端实时控制

**官方当前公开模型信息**：Jev 1.13.0 由 /v1/systemone 服务；输入只支持文本、JSON 对象或文本数组；上下文总预算 64k token，state 加最长单题预算 32k；文档明确英语是主要训练语言，其他语言含 CJK 可处理但表现不等。模型页面列出限流和价格，同时提醒服务限制会动态变化。目前没有公开下载权重的本地部署路径。这些条件适合联网的研发主机工具，不适合把 API 连接加入手机启动、调度或中断决策。

## 19 隐私、对抗输入和韧性

官方称客户请求不用于训练，但研发日志本身可能包含客户标识、路径、内部符号、固件信息和未发布缺陷；不能因此默认可以外发。按公司政策做脱敏、访问控制、日志保留与供应商审批；确认账号合同的 retention / ZDR 条件。服务端可能限流或不可达，所以加超时、重试预算、断路器和回退到现有队列。存储模型版本、题目 schema、输入 hash、概率与人审标签以便追踪。升级 jev-latest 可能改行为，生产评测使用 pin 版本。

## 20 四阶段试点

建议第一阶段选一个低风险、有历史数据的工作流。盘点最近两个发布周期并由工程师双标；离线回放时统一输入、标签和数据切分，和规则、encoder、通用 LLM 对比；通过后影子运行，只记录建议，不改变任何 CI / release 行为；最终只把低风险 owner 建议限定上线，保留开关和回滚。每阶段设退出条件。如果主要错误来自输入质量或标签争议，应先修采集和 schema，而不是迭代 prompt 来掩盖数据问题。

## 21 上线验收指标

除 overall accuracy 外，报告 macro F1、每类 recall、严重类漏报、ECE / Brier、reliability bins、risk–coverage、p50/p95、成本、429 / timeout 和回退比例。按子系统、设备 revision、kernel branch、发布阶段、语言、输入长度切片。测试集留出较新的软件版本，检验分布漂移；不要让同一设备或同一故障家族的重复样本跨训练 / 测试集，避免数据泄漏。阈值选择基于团队对“错误 owner”“漏掉 release blocker”等错误成本的量化。

## 22 建议结论

短期建议：用 Jev 作为 CI / VTS 失败语义分流或性能报告排序的实验性服务，且严格限定它只生成建议。首先对比已有规则和监督 encoder。若要上生产，只对低风险、易回退的路径自动执行；release blocker、设备刷写、kernel 配置更改、回滚和发布仍由确定性检查与授权人控制。如果内部数据不允许外发，直接把本地 encoder / 规则设为主要路径，不要把数据治理问题变成绕过约束的 API 代理。

## 23 来源与讨论

资料列表放在资料来源.md。可与听众讨论三个工程问题：哪些 CI/VTS 失败目前最耗费 owner 归因时间？哪些 Perfetto 指标已经被统一抽取为 schema？日志离开内网的边界在哪里？确定第一批数据集与错误成本后，才有条件判断 Jev 值不值得接入。所有数值需按当前模型版本与团队环境重新测量。

## 设计评审时的建议问题

1. 第一试点的标签是否互斥、定义是否可操作，unknown 是否允许？
2. 哪种错误更贵：错分 owner、漏掉高严重度问题，还是误报？
3. 哪些字段可以离开设备实验室内网？是否需要本地匿名化？
4. 现有规则 / encoder 基线是什么，是否能用同一冻结测试集比较？
5. API 不可达、语言切片退化、模型版本变化时的回退方案是什么？
