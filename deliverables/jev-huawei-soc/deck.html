02定位 · 工程判断

先在研发工具链试点，别进内核热路径

它适合做异构日志的语义分流，不是可直接烧进手机的本地模型
编译 / CI日志分类 · 失败分流
→
性能 / 功耗特征归因 · 回归排序
→
代码 / 设备动作确定性校验 · 人工签核
边界：研发主机或 CI 服务侧的建议能力；不进入调度器、驱动、中断或启动关键路径。
03模型接口 · TypeSafe API

Jev 回答判断题，不负责写解释

把非结构化问题转为预先定义的输出空间
STATE日志 + 指标 + 设备 / 构建上下文
→
Jev 1.13对问题并行评估
→
ANSWERStyped 选择、分数、是 / 否概率
输入支持 string / JSON / 文本数组；输出可直接供程序读取。类型约束不代表语义结论总正确。
04模型接口 · 三种原语

Choice、Score、Noul 解决不同判断

先定义输出空间，再把问题交给模型
Choice这个失败最像哪个子系统？driver 0.74 · HAL 0.18 · kernel 0.08
Score这次性能退化严重度在哪一档？0–3 档的概率加权位置
Noul故障是否只发生在特定 SoC revision？P(yes) = 0.82
Score 是序位分布的期望位置，不是物理量；Noul 不返回 confidence 字段。
05方案比较 · 工程基线

选择取决于数据、时延和部署边界

建议和规则、本地 encoder 以及通用 LLM 同台比较
方案适合代价 / 边界
规则 / parser格式明确、可验证的条件和数值计算措辞变化会让规则变脆
本地 encoder有标签、高吞吐、离线、本地数据需标注和版本维护；新类目要更新
通用 LLM解释、总结、开放式推理、代码生成自由文本需校验；时延 / 成本较高
Jev固定问题空间、概率分流、零样本启动托管 API、英文优先；本域表现需实测

07可靠性 · TypeSafe Confidence

置信度适合分流，不等于正确率保证

校准是群体属性，不能把 0.9 解释成这一条有 90% 把握正确
概率分布Choice / Score 的各类概率
→
阈值验证reliability · ECE · Brier
→
工程动作低风险自动分流 / 高风险人审
按误报与漏报成本分别定阈值；再看 risk–coverage，验证自动覆盖率升高时错误如何变化。
08可靠性 · 官方 Jev 1.13 Jaggedness

已知弱点决定预处理和降级策略

模型适合语义判断；把数学、计数、日期比较留给代码
字面理解 / 否定“未复现”与“已复现”容易受上下文影响结构化字段，明确正反条件
数值与日期不要让模型算 p95、频率差、时间窗parser / SQL / 代码
长 state / 无关内容噪声会降低判断质量并增加成本先筛选、去重、聚合
对抗性文本日志内容可改变模型判断state 当不可信数据，做注入测试
中文 / 多跳推理CJK 并非主要优化语言，多跳更脆弱分语言、分难度评测；保留 unknown
以上限制来自 TypeSafe 自己的 1.13 文档，版本升级后也要重新回归。

13SoC 用例 · 用例一 · CI / VTS

失败日志可自动分流，不自动改代码

适合样本量大、owner 难找、历史失败重复出现的模块
输入test timeout · board R2 · kernel build 8421保留原始 log 与测试 ID
计算重试率、版本差异、首次失败时间代码做精确比较
JevChoice：clock / power / driver / HAL / unknown给概率，不写根因长文
动作建议 owner、附证据片段、相似问题链接人审后回填标签
不允许模型结论直接改代码、刷机、重启设备或关闭 release blocker。
14SoC 用例 · 用例二 · trace 分析

数值归因留给PerfettoSQL 和代码

Jev 负责“更像哪类回归”；指标与差值由确定性脚本计算
Perfettosched / freq / GPU / power / logs
→
SQL / parserwake-to-run p95 · jank · 频点驻留
→
Jevscheduler / GPU / thermal / I/O
功耗 rail 数据依设备支持而异。先规范 trace 配置与窗口，再让模型读小而相关的特征摘要。
15SoC 用例 · 用例三 · 跨版本兼容性

Bring-up 归因要保留版本上下文

相同错误行不代表相同根因；设备与软件配置必须跟随样本
硬件维度SoC revision · board · PMIC · memory SKU决定问题是否局限某一物料组合
软件维度kernel branch / config · firmware · HAL version由脚本精确定位首次变化版本
环境维度cold / warm boot · 温度档 · lab station · test ID分清偶发和稳定复现
Jev 判断相似故障族 · 疑似共同依赖 · 建议 owner不把相关性当成已验证 root cause
版本比较、回归区间和频率由代码计算；模型只辅助解释语义相似度。

17集成设计 · 目标架构

本地抽取与策略，托管服务只做语义判断

把 Jev 当可替换依赖；服务异常不阻断 build、test 或刷机
设备 / 测试场logcat · tombstone · Perfetto
→
研发主机脱敏 · SQL · 去重 · 压缩 state
→
Jev API固定版本 · typed answer
→
研发闭环建议 owner · 人工确认 · 标签回流
原始数据留本地，外发字段最少化；不允许调用外部服务时，替换成本地 encoder 或规则。
18部署边界 · 官方 Models 文档

托管服务与手机端实时控制不是一回事

Jev 当前以 API 方式提供；未公开可下载权重，输入仅文本
研发云 / 实验室主机 · 可试
CI、夜间回归、性能报告
建议式分流，可设置超时与回退
网络服务 · 官方 70–500ms
实测要加地域、排队、TLS 与限流
手机运行时 / 内核热路径 · 当前不适合
调度、IRQ、DVFS、启动决策
需要硬实时、本地和确定性路径
离线 / 隐私约束
用规则或小型本地模型承接
typed 输出不等于实时、安全或离线可用。
19部署边界 · 运行护栏

隐私、对抗输入和韧性仍由系统负责

TypeSafe 明确 state 可能含有影响答案的误导文本
隐私脱敏序列号、路径、客户内容；按数据级别审批外发不允许外发就切本地方案
可复现pin jev-1.13.0；记录输入 schema、模型版本和概率升级模型重跑评测
安全日志全都视作不可信数据；覆盖注入和错误根因样本unknown / 人工复核
韧性超时、429、断网、响应异常都走原流程不阻塞 CI / 刷机
官方称客户请求不用于训练；数据保留、零留存与企业条款仍需按合同核验。
20试点方案 · 最小验证路线

先离线回放，再影子运行

首个试点选“CI 失败 owner 建议”或“性能回归排序”，不碰发布自动放行
01 · 盘点整理近两个发布周期样本，工程师双标代表数据先确认标签一致性
02 · 回放同一冻结集比较规则、encoder、Jev、通用 LLM按版本 / 子系统切片
03 · 影子只生成建议，不修改 CI 状态或工单 owner记录采纳 / 误导 / 不确定
04 · 限定上线仅低风险自动分流；门禁仍走现有策略保留回滚与审计
先固定语言、日志抽取 schema、阈值和版本，再讨论扩大覆盖。
21试点方案 · 上线验收

用风险覆盖率决定自动化边界

准确率之外，还要衡量严重少数类和错误自动化的代价
Macro F1 / per-class recallowner 错分会把问题送错团队subsystem · rare faults
ECE / Brier / reliability bins概率与命中率是否匹配版本 · 语言 · 问题类型
Risk–coverage自动处理覆盖增加时错误如何变化按错误成本分层
p50 / p95 / cost / retry在真实地域、负载、限流下测服务链路输入长度 · 网络地域
测试集按设备 revision、kernel branch、release 阶段、English / 中文拆分，并和现有基线同场比较。
22结论 · 给 SoC 软件团队的建议

从低风险研发流程开始验证

Jev 可以减少“判断步骤”的成本，但不能替代确定性工程机制
先试 CI / VTS 失败分流与性能回归排序
Jev 判断语义，代码计算数值并执行策略
低置信、未知故障、中文弱项、服务超时回到原流程
只有本域评测优于规则、encoder 与现有流程，才逐步扩大范围
