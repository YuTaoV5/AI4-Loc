# 解释与证据检查表

- inventory.json 只是一份有采样边界的索引；文件名匹配、关键词匹配、设备属性均需回看原文，不能当根因结论。
- 命令失败文件可能名为 kernel_log.txt、dmesg.txt、last_logcat.txt。包含 Permission denied、Operation not permitted、failed to read、Can't open 等输出时，核实是否只有失败信息；这代表抓取限制。
- 当前启动、上次启动、抓取时刻、固件相对 tick、kernel uptime 和墙上时钟并不相同。报告要标明不能对齐的时间域；一个 ZIP 中的文件也不一定来自同一次启动。
- 先用设备/构建属性建立身份，再寻找 reset/boot reason、存储/DDR 初始化异常、镜像完整性失败、运行时异常、挂起和服务反复退出。没有早期串口记录就列为缺失，不反推失败点。
- 证据不足时，下一步应具体：补取哪次启动哪个阶段的记录、可信解码器版本或与日志对应的符号/源码产物；不要求用户在网页手填 commit。
- 普通 Linux 回归输入不一定来自手机；正常使用既有故障证据与调用方 JSON schema，不输出目标机型假身份。
- 每条引文都要在文件中存在，行号来自实际计数；只有地址时记录地址，不编造文件路径或符号。
- 不以 ERROR 级别直接判异常，不以发生在最后的事件直接判根因，不以加密/缺失日志判硬件坏件。
- 合成案例只验证受控机制与证据链，不把合成分数推广到真实手机；真实无标签包不能生成根因准确率。
