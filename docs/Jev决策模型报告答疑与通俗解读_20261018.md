## 先给出报告可以站得住的中心论点

**我们在研究怎样把定位过程中的有限判断做得更便宜、更可控，而不是已经证明“换上Jev就能更快找出所有根因”。**

目前证据支持：部分有限选择场景使用Decision更快；针对首诊断标签微调9B模型能提高这组分类成绩。尚未证明：专有Jev架构已复现、RLCD是提升的唯一原因、小模型普遍胜过27B、概率已可靠校准、完整根因与引入提交定位显著改善。

## 名称对照：这些不是同一个模型

| 名称 | 小白可以怎样理解 | 本项目实际做到了哪一步 |
|---|---|---|
| TypeSafe Jev | 厂商的专有“读材料、做类型化判断”的模型服务 | 本轮公开实测没有直接测其正式API；不能把本地成绩当官方Jev成绩 |
| SGLang Jev-like / Decision | 给现有聊天模型提供“直接读选项分数”的接口 | 已测本地通用27B，以及9B基座和微调权重；接口相似不等于内部架构相同 |
| PPLX-Decider-v1-27b | 另一套真实、专门训练的决策权重 | 已测固定版本，先CPU卸载，后完整GPU分时复测；不是TypeSafe Jev |
| nanojev | 第三方对专有Jev的假设性重建项目 | 本项目证据中没有它在内核数据上的独立实测；不可把9B结果改名为nanojev结果 |
| Laya | 开源决策模型与训练/推理工具 | 本项目参考固定版本的思想，没有照搬其编码器和决策头 |
| 本项目Qwen3.5-9B决策适配 | 已读过大量资料的9B模型，再补习本任务的标签与判断习惯 | 真实完成LoRA+CE/RLCD训练、分类复测、并发测量与完整Agent小规模检查 |

SGLang官方文档说明其通用Decision从答案位置的next-token分数读概率，不要求专门决策权重；nanojev作者将其明确称作假设性重建。分别见[SGLang](https://docs.sglang.io/docs/supported-models/decision_models)、[nanojev作者仓库](https://github.com/sshh12/nanojev)。

## 核心问题一：Jev的效率提升从哪里来？关闭thinking的Chat还差多少？

### 先把一趟请求分成几笔账

可以把模型比作阅卷老师。一份长材料先要读完，再决定答案，最后可能还要写一大篇解释。

```text
总时间 ≈ 排队 + 读输入(prefill) + 逐字输出(decode) + 网络/框架开销

长篇Chat       读材料 → 判断 → 写解释、答案、JSON等许多token
关闭thinking   读材料 → 判断 → 仍要输出答案文本
单字母Chat     读材料 → 判断 → 只输出A/B/C中的一个字母
本地Decision   读材料 → 判断 → 直接返回这些字母的归一化分数
```

“关闭thinking”表示不生成那段显式推理文本，不表示神经网络不做计算。单字母Chat依然执行输入前向，Decision也依然执行输入前向；二者共同的大头并没有自动消失。

减少长篇解释通常能省下很多解码步骤；如果对手已经只输出一个字母，可再省的输出工作就很少。长日志、排队和模型前向占比越大，接口差距越容易缩小。这是根据执行流程作出的解释，不是我们已经逐个CUDA内核完成了因果分摊。

官方Jev还强调专用架构、并行输出和RLCD训练，但厂商整体系统的宣称不能直接移植到本地SGLang接口，更不能说我们已经验证了相同数量级的提速。见[TypeSafe官方介绍](https://typesafe.ai/blog/introducing-system-one-models-and-jev)。

### 本项目对照到底是多少？

| 实验 | Decision | Chat | 可以怎么读 |
|---|---:|---:|---|
| 10月11日，27B三个分类字段，Chat已关闭thinking | 1.145秒 | 2.075秒 | 耗时减少44.8%；Chat还要生成结构化字段，输入组织也不同 |
| 10月16日，27B单任务单步，冷条件、单字母Chat | 0.868秒 | 0.866秒 | 基本没有优势 |
| 10月16日，27B四任务×八步，预热、单字母Chat | 3.634秒 | 4.085秒 | 整批耗时减少11.0% |
| 10月16日，微调9B单任务单步，冷条件、单字母Chat | 0.2731秒 | 0.2739秒 | 近乎相同 |
| 10月16日，微调9B四任务×八步，预热、单字母Chat | 1.2803秒 | 1.3876秒 | 整批耗时减少7.74% |
| 10月16日，微调9B四任务×八步，冷条件 | 2.3573秒 | 2.2639秒 | Decision反而慢约4.1% |

上表不是可拼成一条曲线的统一实验。旧三个字段的输出负担与新单字母基线不同；27B和9B的权重、配置及测量时段也不同。新性能实验每格5次，整批时间是最后一个任务结束，不是单次TTFT。Decision不输出文本，应称“完整概率可用时间”；Chat的首内容时间另外记录。

新实验的两接口完整prompt token ID逐项一致，比旧三字段对照更能控制输入差异。但冷/热、状态池、调度仍会影响差值，不能把7.74%的全部差异断言为某一个内核的贡献。

**可以这样回答：**“最大的潜在收益来自不用逐字写答案；当Chat也关掉thinking并只回一个字母，差距就小得多。我们八步预热实验约快7%–11%，单步近似持平，有些冷条件还更慢。没有证据说任何场景都快一个数量级。”

证据：[旧接口研究](../research/decision-localization-20261011/report.md)、[27B并发报告](../research/kv-concurrency-20261016/REPORT.md)、[9B对照表](../research/jev-qwen35-9b-20261016/tables/checkpoint-concurrency-summary.csv)。

## 核心问题二：专门训练的PPLX为什么没赢，还更慢？

### 先纠正“效果不好”这个前提

在全GPU复测中，PPLX与通用模型的既有test都为27/27调用与标签吻合，实际上只有9个唯一案例、每例重复3次；25例代理标签也都是23/25。**这叫没有显示分类优势，不叫已经证明准确率差。**

这9例太容易或覆盖太窄，都可能让比较碰到“天花板”：两位老师都把这张小测验做满分，不能据此判断谁在新难题上更强。35个不支持现有真值映射的案例只保存输出，没有硬凑准确率。

### 慢，要分两轮解释

| 部署条件 | PPLX均值 | 同轮通用方案均值 | 能说明什么 |
|---|---:|---:|---|
| 旧CPU卸载，与通用模型共存 | 19.455秒 | 1.485秒 | CPU/GPU搬权重影响很大，不能作为公平的权重速度比较 |
| 后续全GPU、同一A100分时独占 | 5.672秒 | 2.563秒 | 排除了权重CPU卸载；已测PPLX方案仍更慢，约为通用方案2.21倍耗时 |

后一个对照很重要：不能继续拿CPU卸载解释全部差距。但它仍不是“只换权重”的实验。PPLX采用官方参考Transformers/SDPA，通用模型采用SGLang；提示编码、专用读出和执行方式也不同。三问题在PPLX适配中组成三行输入批处理，不是证明长状态只算一次。输入token总数也为325,638对302,931。两阶段固定先后，没有AB/BA交叉顺序。

输入token约多7.5%，不能在没有分项计时的情况下说它解释了约121%的耗时增加。运行时、内核、批处理和提示差异是应检查的因素，而不是已经分清贡献的故障根因。

PPLX模型卡称其从Qwen3.8-27B微调；“训练过决策能力”并不表示模型变小、权重更少或一定采用最快执行引擎，也不承诺对内核日志这一领域一定更好。见[PPLX原版本模型卡](https://huggingface.co/perplexity-ai/pplx-decider-v1-27b)。

还应纠正一个比较对象：这一轮通用端也返回零文本的Decision结果，不是直接做“PPLX对单字母Chat”的新对照。不能把三个不同实验中的耗时接起来当配对实验证据。

**可以这样回答：**“PPLX这次不是分类更差，而是没比通用模型多答对，部署还更慢。最初有CPU搬运问题，后面完整GPU重测仍慢；但两边推理引擎不同，所以目前只能评价已测部署方案，不能断言专用训练本身让模型变慢。”

证据：[全GPU报告](../research/pplx-timeshare-20261012/REPORT.md)、[冻结统计](../research/pplx-timeshare-20261012/results/statistics.json)、[实际适配代码](../research/pplx-timeshare-20261012/serve.py)、[CPU历史报告](../research/pplx-decider-20261011/REPORT.md)。本文只针对已测v1固定revision；未测后续版本不作结论。

## 核心问题三：nanojev好，是任务微调的功劳吗？小模型微调能取代27B吗？

### “nanojev”与我们的9B，先分开

nanojev作者公开的是Qwen3.5-4B-Base、LoRA及pointer head的组合，并报告使用带标签数据训练、温度校准和共享状态缓存；作者报告的评测不是本项目内核定位。作者README给出约90.7%的自有评测准确率，这是外部自报，不是我们的复测结果。它采用标签监督，因而不能当“完全没训练也很好”的证据；缺少针对我们任务的严格消融，也不能说好结果只来自微调。见[nanojev原作者说明](https://github.com/sshh12/nanojev)。

本项目做的是另一个实现：Qwen3.5-9B加LoRA，保留原LM字母读出，没有nanojev的pointer head，也没有在八题实验中实现它的共享状态分叉路径。两者不要统称为同一个“nanojev模型”。

### 我们自己的微调，改善了什么？

| 指标 | 9B基座 | 9B微调后 | 解读 |
|---|---:|---:|---|
| 首诊断分类多数票 | 66/87，75.86% | 78/87，89.66% | 增加13.79个百分点 |
| 警告/panic类别 | 8/20 | 19/20 | 增益主要集中在这个标签边界 |
| locking类别 | 0/2 | 0/2 | 没有改善 |
| blocked task类别 | 2/2 | 1/2 | 出现退化 |
| NLL，T=1，越低越好 | 0.830 | 1.724 | 部分错误变得更自信 |
| 完整Agent源码位置命中，每种流程 | 2/3 | 2/3 | 小规模检查未显示定位提分 |

Decision和单字母Chat的分类成绩都从66升78。这说明训练改变了这个任务的答案倾向；不能把相同提升归因于Decision接口独有的能力。

**最有支持的解释是“本任务的监督适配有效”**，尤其是学会了我们怎样区分第一条警告与保护异常。不是已经证明它学会了更深的并发因果推理。只有33训练、4开发案例，测试87例来自20机制簇且历史材料被开发者见过；没有多随机种子、等预算CE-only或新机制盲测。测试也没有OOM和watchdog样本支持。

### 为什么还不能说“小模型胜过27B”？

需要回答的是同一张试卷、同样资料与工具下谁更好。现有9B和27B研究并非统一数据、统一完整Agent任务、统一推理配置下的尺寸消融，Qwen代际也不同。不能把9B在87例弱标签分类的89.66%，与27B在9例旧分类的9/9或另一组源码定位分数直接排榜。

比较稳妥的路线是：让轻量或微调模型处理重复、边界清楚的分类和工具路由；复杂源码调查交给Chat、符号化、静态/动态工具及验证。**这是值得检验的系统设计，不是本项目已经证明最优的组合。**

事实上，现有独立32k实验里，微调后混合Agent三例耗时合计29.247秒，纯Chat23.229秒，位置命中都2/3；这就是暂不宣称“混合一定更好”的直接理由。

**可以这样回答：**“微调小模型值得做，因为它能学会本领域的判断口径；但我们目前只证明首诊断分类有所改善，没有证明它比27B更会找根因，更没有证明它能取代源码工具和复杂推理。”

证据：[9B完整报告](../research/jev-qwen35-9b-20261016/REPORT.md)、[分类表](../research/jev-qwen35-9b-20261016/tables/accuracy-by-kernel.csv)、[完整Agent汇总](../research/jev-qwen35-9b-20261016/tables/agent32k-aggregate.csv)。

## 核心问题四：Laya的训练真是Jev的方法吗？微调到底怎么做？

### 同一个方法名字，不等于拿到了同一份配方

TypeSafe公开提到RLCD，即“为了校准决策而进行的强化学习”。Laya也使用RLCD这一名称和概率评分思想，并提供开源实现。但目前查到的一手资料不足以证明Laya逐项复现了TypeSafe专有模型的训练数据、奖励、网络、采样与训练日程。**正确表述是“参考公开决策训练思想的开源实现”，不是“官方Jev训练配方已被证实”。**

架构也不同：Laya发布的主要模型使用BERT类编码器；本项目保留Qwen因果骨干；nanojev使用自己的pointer读出设计。这些都能做有限决策，但不是同一张网络。见[Laya本项目参考的固定版本](https://github.com/NandhaKishorM/laya/tree/4ac226d5ee88ed6df8db288a05c766d7a34ee682)、[TypeSafe原始介绍](https://typesafe.ai/blog/introducing-system-one-models-and-jev)。

### 用“给老师补习”理解本项目微调

1. **保留原有知识。** 下载固定版本的官方Qwen3.5-9B，冻结大部分原权重，不是从随机参数重训9B。
2. **准备习题和判分口径。** 从日志构造脱敏首诊断窗口；按机制分组为33训练、4开发、87测试，监督标签是首诊断家族。
3. **装一个小的可调支路。** 在48处文本投影加入rank8、alpha16的LoRA，只训练5,308,416个参数，约为总参数0.056%。可理解成“加少量可调的知识修正”，不是改写全部书本。
4. **打乱答案位置。** 每案例每轮4种选项排列，选项数5/8/12，降低只记“A总是对”的风险；这不保证消除其他捷径。
5. **先练答对。** 第0轮用交叉熵CE：真实类别概率越小，处罚越大。
6. **再练概率判断。** 第1–2轮加入Laya式RLCD：在选项logits上采4组中心化高斯扰动，计算log加spherical奖励，比较组内相对奖励形成更新方向，同时保留CE。
7. **累计更新。** BF16骨干，FP32适配器与AdamW；学习率1e-4，每4微步更新一次，3轮396微步，共99次参数更新。
8. **用开发集选版本。** 选中epoch1，即从0起算的第二轮；温度选为0.5。开发只有4例，这个选择不稳定，不能当普适最优配置。
9. **合并并实测。** 把LoRA增量合并成BF16模型，再在同一SGLang中测基座与训练后模型，避免拿离线Python分数冒充实际服务结果。
10. **检查负结果。** 分类提升，但NLL恶化；完整Agent位置命中未升。结果必须一并报告。

LoRA的简式为`有效权重 = 冻结权重W + 2BA`。A随机初始化、B初始为零，因此新增支路初始输出为零；保留原LM字母读出，没有新建随机决策头。

### RLCD为什么不等于“神奇地学会诚实”？

交叉熵已经是一种概率训练目标。RLCD的想法是用概率质量的奖励引导学习，而不只奖励选对第一名。理想的概率评分规则可以鼓励诚实报告分布，但仍需要合适标签、足够样本与优化条件；不能从数学上的奖励性质直接推导部署概率必然可靠。

本项目奖励还包含log下限−9.21、有限4次扰动和优势标准化，不能宣称数值实现具有全域严格恰当性或无偏梯度保证。没有“只用CE、相同更新数”的对照，无法拆出CE、RLCD、选项排列和开发选点各自的贡献。

真实日志最后一个微步在290.764秒，控制器到评估、导出与哈希结束343.689秒。第一步记录约57秒，包含首次编译；不是“预训练9B只花六分钟”。较早报告摘要对编译排除的措辞不准确，计时以[逐步日志](../research/jev-qwen35-9b-20261016/training-steps.jsonl)和[完成记录](../research/jev-qwen35-9b-20261016/training-complete.json)为准；前置加载不包含在该训练循环时钟内。

**可以这样回答：**“我们借鉴Laya的概率训练思路，在现有Qwen上训练很小的LoRA补丁。不能说这就是官方Jev内部配方；也没有消融证明RLCD比普通监督微调更好。当前最可靠的说法是：这个完整训练方案让一组首诊断分类更准。”

实现依据：[训练代码](../research/jev-qwen35-9b-20261016/train.py)、[冻结训练参数](../research/jev-qwen35-9b-20261016/training-protocol.json)、[训练环境](../research/jev-qwen35-9b-20261016/training-environment.json)、[合并验证](../research/jev-qwen35-9b-20261016/merge-validation.json)。

## 还容易被追问的20个问题

### 5. 这不就是一个分类器吗？为什么还要叫决策模型？

对于本项目固定的首诊断家族，它确实承担分类器的工作。决策模型接口还允许输入问题、候选项和判定标准；能否对新问题泛化，要另测，不能仅凭接口支持动态选项就认定模型懂任意问题。普通分类器、规则和小编码器都应该成为基线。

### 6. 为什么不直接用正则匹配KASAN、RCU、OOM？

应当先测规则。如果目标只是识别明确检测器名称，规则可能又快又准。模型应证明自己能处理含糊窗口、多个检测器、缺失信息或新措辞。现有87例分类还有规则选出的诊断窗口，本身不是从全部原始日志里独立找第一现场。把规则能解决的题当成模型独有能力，会高估研究价值。

### 7. 关闭thinking，是不是就“不推理”了？

不是。它仍用所有网络层处理输入，只是不输出显式思考文本。我们没有测模型内部是否存在“隐式推理”这一认知概念，报告只说关闭了哪项生成配置。

### 8. “一次前向返回概率”是不是不用读日志？

不是。长材料仍要被编码。就像不写解题过程也得先读题。专用架构、共享状态或缓存可能减少重复计算，但必须检查实际实现，不能从零输出token推出零输入成本。

### 9. 一次HTTP放8题，是不是状态只算一次？

不是必然。本项目SGLang八题仍有八个渲染后的内部评分prompt，前缀是否复用由实际缓存命中决定。HTTP批处理、调度批处理、共享状态编码是三个不同概念。nanojev作者的状态缓存分叉也不是我们已经实测的路径。

### 10. 既然不生成文本，为什么KV内存没降？

输入本身就占KV，服务还预留固定池；混合注意力另有线性状态槽。只少一个输出字母，通常不会让整块预留池消失。微调9B四任务八步预热的平均活跃KV峰值，Decision/Chat为458.219/458.125MiB，状态峰值16/13槽，没有节省证据。原27B每token KV较大，是模型结构差异，不能归功于接口。

### 11. 为什么参数里写四并发，实际只有一个？

线程参数不等于模型有足够状态容量。旧生产配置的线性状态池只有9槽，每请求预算5槽，向下取整只够1。隔离实验扩大到32槽后才确认有效容量4。像餐馆有四个服务员，却只备了一套餐具，仍无法同时招待四桌。

### 12. softmax的0.9是不是“有90%概率根因正确”？

不是。它先是“在所给候选、当前模型和温度下”的分布。如果真根因没列入选项，几个错选项的概率照样加起来为1。还必须在独立同分布数据上检验校准，且首诊断概率不能改名为根因概率。

### 13. 准确率变好，为什么NLL反而更差？

准确率只看第一名，NLL还看真答案分到了多少概率。把10道题里的更多题答对，却对少数错题极其自信，NLL就可能恶化。例如真答案概率从0.2变成0.001，单题处罚从约1.61升为6.91。这个例子是数学示意，不是某个具体实测案例。我们的微调就是“分类改善、NLL恶化”的真实反例。

### 14. 温度校准是不是重新训练了一个更聪明的模型？

通常只是把同一组选项logits拉平或拉尖，正温度不会改变同一向量的第一名。T较小更尖，较大更平；它不能修复缺失选项或错误知识。本项目4例开发集选出的T=0.5使测试NLL进一步变差，不能推荐为可靠生产置信度。

### 15. 类型安全是不是不会“幻觉”？

类型安全约束的是输出能被程序读取，例如只允许A/B/C；模型仍可能自信地选错B。能选出格式合法的错误答案，与“生成一个不存在的字段”是不同问题。报告应说“减少自由文本/格式错误”，不要说“保证判断正确”。

### 16. 第一诊断、故障家族、源码位置、根因、坏提交有何不同？

“探测器先报警”是第一现场；“疑似内存生命周期问题”是家族；“栈里这个函数/行”是位置；“另一线程提前释放对象”是因果机制；“哪个提交引入释放顺序变化”是提交归因。五个层次逐个需要真值和验证。现有分类分数不能顶替后四项，源码区间命中也可能只是命中报错现场。

### 17. 注入的是watchdog，模型说RCU，是答错吗？

先看问题问什么。故障注入类别不一定等于第一条诊断。已有LOOP/SOFTLOCKUP案例首先出现RCU stall；问第一诊断时选RCU有理由。我们保留原评分，不为抬分事后改标签，但应补独立标注，避免把不同构念混成“准确率”。见[标签差异分析](首诊断与故障注入标签差异分析_20261011.md)。

### 18. 87个测试案例足够吗？为什么重复3次不算261个独立样本？

同一机制的不同日志以及同一案例换选项顺序，都共享大量信息。重复测量能看稳定性，不能变出新故障机制。87例对应20机制簇，置信区间应考虑相关性；微调差的机制簇区间触及或跨过0，不能只看13.79个百分点就喊显著泛化。

### 19. 做了匿名目录，能保证没有标签泄露吗？

匿名目录、只读输入、不给Agent挂载gold等措施能阻止一些直接泄露。日志里的注入函数名、负载名、重复机制和历史开发接触仍可能是捷径；预训练是否见过公开材料也无法由目录隔离证明。应分别检查字段、文件权限、文本线索、数据去重和开发过程，而不是给出绝对“零泄露”结论。

### 20. 历史9/9和新89.66%，是不是模型退化了？

分母、标签集合、案例难度、模型和实验日期都不同，不能直接相减。9/9也不是证明真实准确率100%。每个数字旁要有“哪一组数据、哪种目标、多少独立单位”。

### 21. 定界更快，为何完整Agent反而慢？

额外一次Decision可能增加等待，还可能引出更多检索或修复调用。只加一个更快的小步骤，不代表总链条变短。32k三例检查中，基座混合10次HTTP、53.464秒；微调混合6次HTTP、29.247秒，虽有改善，仍高于微调纯Chat3次HTTP、23.229秒。相同2/3命中不能说定位质量已提高。

### 22. 现在能不能让高置信Decision直接决定后续工具？

可以作为待验证设计：用于推荐、排序或带回退的路由，保留证据和修正机会。没有校准验证前，不应让一个0.99概率永久屏蔽其他候选。阈值应由新数据上的错误率、覆盖率和误判代价决定，不预设0.9必然安全。

### 23. 要证明微调小模型是正确路线，最缺哪个实验？

冻结全新机制测试集，训练和开发过程都不接触它；在相同输入与工具条件下比较小/大模型的基座、CE、CE+RLCD。优先采用同代同系列，若只能用不同代模型，应明确混杂。报告类别宏平均、逐类支持、校准、失败率、端到端位置/机制/提交验证，以及时间、token、HTTP和工具预算。新路线必须在完整定位上也有收益。

### 24. 这个项目现在最有价值的贡献是什么？

是把模型判断、工具证据、隔离评测和运行时观测接成可审计流程，并用反例限制夸大的结论。接口能更快返回，不表示根因更准；专用权重不一定是当前硬件上最快部署；微调提高标签一致性，不保证概率或因果推理同步改善。这些区分能帮助后续实验把钱花在真正的瓶颈上。

| 接口是否省时 | 同权重、同完整prompt token、同输入与缓存、同引擎 | Chat多字段 / 单字母 / Decision；都关thinking | 结果可用、首内容、请求完成、排队、prefill、输出长度 |

## 小白术语速查

| 术语 | 直白解释 |
|---|---|
| 参数 / 权重 | 模型从训练中学到的数字；9B约指90亿参数，不是每次回答消耗90亿token |
| token | 模型处理文字的小片段；不固定等于一个汉字或一个单词 |
| prefill / decode | 前者处理已给的输入，后者逐步生成输出；关thinking主要减少显式生成，不免除读输入 |
| KV cache | 保存注意力计算中的中间结果以便复用；不是存放最终答案的普通文本缓存 |
| 读出 / 决策头 | 把模型内部特征变成选项分数的出口；接口名相同不代表出口和骨干都相同 |
| LoRA | 给冻结大模型加少量可训练的低秩增量；训练参数少，不等于部署时只运行这几个参数 |
| CE | 交叉熵，用真答案概率训练模型；也是概率训练，并非只有RLCD才会训练概率 |
| NLL | 真答案负对数概率，错得很自信会罚得很重，越低越好 |
| Brier / ECE | 前者看概率分布和标签的平方误差，后者把置信度分箱后比较平均信心与命中率；视角不同，不能任选好看的一个 |
| 校准 | 大量同类预测说“八成把握”时，实际是否大致八成正确；不是保证当前这一题正确 |
| 消融 | 固定其他条件，只去掉或替换某一部分，检查这部分到底贡献多少 |
| 百分点 / 耗时减少 | 准确率75.86%到89.66%约增加13.79个百分点；耗时1.388到1.280秒约减少7.74%，不要混用 |
